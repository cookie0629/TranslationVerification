# HW5 — отчёт о проверке модели «запрос — ответ»

## Объект и границы проверки

Модель повторяет граф P09: `s0=idle`, `s1=req`, `s2=ack`, `s3=error`; начальное состояние `s0`. Исходные переходы: `s0→s1`, `s1→s1/s2`, `s2→s0`, `s3→s3`. Никакой справедливости нет, поэтому вечный выбор `s1→s1` разрешён. В исправленном варианте удалён только этот переход. Значения `state` конечны; у каждого состояния есть следующий шаг, поэтому искусственных тупиков нет. Проверка касается только этой абстрактной модели, а не произвольной реализации протокола.

Команда проверки: `python run_checks.py --exe ПУТЬ_К_nuXmv`; внутри выполняется `nuXmv -s models/request_response_bug.smv` и аналогичная команда для `fixed`. Использован nuXmv 2.0.0 (связанный с NuSMV 2.6.0), стандартная пакетная проверка BDD. SAT/BMC, fairness, POR и bitstate не использовались; A/B-сравнение с другим инструментом не проводилось. Полные журналы: [исходная модель](logs/bug.nuxmv.txt), [исправленная модель](logs/fixed.nuxmv.txt).

## Свойства и фактические результаты

| ID | Смысл | Формула | Bug | Fixed |
| --- | --- | --- | --- | --- |
| S1 | Ошибка недостижима | LTL `G !at_error` | true | true |
| S2 | Подтверждение возвращает к ожиданию за один шаг | LTL `G (at_ack -> X at_idle)` | true | true |
| S3 | После запроса следующий шаг — ожидание ответа или подтверждение | LTL `G (at_req -> X (at_req \| at_ack))` | true | true |
| L1 | На каждом пути за запросом когда-нибудь следует подтверждение | LTL `G (at_req -> F at_ack)` | **false** | true |
| C1 | Хотя бы на одном пути подтверждение достижимо | CTL `EF at_ack` | true | true |

Все свойства записаны непосредственно в обоих `.smv` файлах. У S1–S3 есть префикс `G`, а L1 является свойством ответа. C1 — обязательная CTL-формула достижимости. C1 **не** утверждает, что ответ неизбежен на каждом пути: существование одного успешного пути совместимо с ложностью L1.

## Контрпример L1 и сокращённая трасса

NuXmv для исходной модели сообщает `G (at_req -> F at_ack) is false` и выводит LTL counterexample. Сокращённый lasso:

```text
Префикс: idle → req
Цикл:   req → req → req → ...
```

В `req` посылка `at_req` истинна, а `at_ack` не становится истинной ни на одном шаге этого бесконечного пути. В полном логе nuXmv после `State: 1.2` повторяющиеся состояния показаны без новых значений переменных: это дельта-печать, `state` остаётся `req`. Указатели `-- Loop starts here` обозначают цикл контрпримера. Более короткого префикса с нарушением нет: начальное состояние `idle` не является запросом. Сам цикл минимален — одна петля `req→req`.

После удаления петли единственный бесконечный путь имеет вид `(idle→req→ack)ω`. Каждый `req` получает `ack` следующим шагом, поэтому L1 становится истинным без добавления допущения о справедливости.

## Обоснование истинных свойств и CTL-свидетельство

Достижимые состояния для обеих моделей: `R0={idle}`, `R1={idle,req}`, `R2={idle,req,ack}`; дальнейшее замыкание остаётся `R2`. `error` не входит в него, что объясняет S1. Из `ack` есть только переход в `idle` — S2. В исходной модели из `req` можно перейти лишь в `req` или `ack`; в исправленной — только в `ack`, что объясняет S3.

Для истинной экзистенциальной CTL-формулы C1 есть кратчайшее свидетельство `idle → req → ack`. Это два перехода; в `ack` истинно `at_ack`. Обратное вычисление `EF`: сначала `{ack}`, затем `{req,ack}`, затем `{idle,req,ack}`. Начальное `idle` принадлежит итоговому множеству. В исходной модели это свидетельство не отменяет контрпример L1: другая ветвь может бесконечно выбирать петлю `req→req`.

## Итог

Три свойства безопасности и экзистенциальная достижимость подтверждены инструментом в обоих вариантах. Требование обязательного ответа нарушено исходным недетерминированным переходом и выполняется после его удаления. Этот результат зависит от указанного графа и отсутствия других действий или задержек; для более реалистичного протокола понадобятся явные таймауты, сообщения и допущения планировщика.
